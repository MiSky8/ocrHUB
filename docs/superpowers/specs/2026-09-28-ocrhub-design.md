# ocrHub — Design Spec

Date: 2026-09-28

## Purpose

A single Docker image that bundles multiple OCR engines behind one
consistent interface, so someone can try and compare several OCR
approaches on their own documents without installing each engine
separately. Built after doing this manually across two prior
OCR-pipeline projects. Published to GitHub and Reddit as a free
dev tool, and secondarily as a credibility/portfolio piece for the
author's automation consulting business.

## Success criteria (v1)

- `docker build` + `docker run` gets someone from zero to OCR-ing a
  PDF or image through a web UI in one command, no manual dependency
  wrangling.
- At least 3 local engines + 1 self-hosted-vision-model path work
  end to end.
- A Reddit post gets a working repo people can actually run, not a
  half-finished demo.

## Scope (v1 engines)

- **Tesseract** (via `pytesseract`) — classic, CPU-only, default-on.
- **pdfplumber** — native text extraction for born-digital PDFs
  (not OCR, but the fast/accurate path when a PDF already has a
  text layer). Default-on.
- **Surya** — modern layout-aware OCR. Opt-in (pulls in PyTorch).
- **PaddleOCR** — opt-in (pulls in PyTorch/PaddlePaddle; previously
  finicky to install — see Risks).
- **DeepSeek vision model via Ollama** — adapter always present,
  "active" only if `OLLAMA_HOST` is set and reachable at runtime.
  ocrHub does not bundle Ollama or model weights.

Out of scope for v1 (candidates for fast-follow): EasyOCR, docTR,
datalab.io API, LandingAI API.

## Architecture

Single Python **FastAPI** application (`ocrhub`). Every engine in
scope is Python-native, so one process is sufficient — no need for
a container-per-engine split.

Each engine is a small **adapter** implementing a common interface:

```python
class OcrAdapter(Protocol):
    name: str
    def available(self) -> bool: ...
    def extract(self, file_bytes: bytes, filename: str) -> OcrResult: ...

@dataclass
class OcrResult:
    engine: str
    text: str
    pages: list[PageResult]
    confidence: float | None
    elapsed_ms: int
    error: str | None = None
```

An engine registry builds itself at startup from whatever adapters
are importable (governed by build-time install) and whatever runtime
config is present (e.g. `OLLAMA_HOST`). `GET /engines` reports which
are available so the UI/MCP client can only offer real options.

Three interfaces share one core service layer — no logic duplicated
per interface:

- **Web UI**: drag-drop a file, pick one or more engines, see
  results side by side (text + confidence + timing per engine).
  Lightweight server-rendered/vanilla JS — no heavy frontend
  framework needed for v1.
- **REST API**: `POST /ocr` (file + engine list), `GET /engines`,
  `GET /health`. OpenAPI docs auto-generated by FastAPI.
- **MCP server**: exposes an `ocr_document` tool over the same
  service layer, using the `mcp` Python SDK in-process alongside
  FastAPI, so agents (e.g. Claude) can call it directly as a tool.

## Data flow

1. File comes in (image or PDF) via UI/API/MCP.
2. If PDF: try `pdfplumber` text extraction first (fast path for
   born-digital PDFs). If the requested engine is an OCR engine (not
   pdfplumber), or the PDF has no usable text layer, rasterize pages
   (`pymupdf`/`pdf2image`) and run each page through the chosen OCR
   engine.
3. If image: run directly through the chosen engine(s).
4. Normalize every engine's output into `OcrResult` (see above) so
   results are directly comparable across engines in the UI.

## Build-time engine selection

Engines are selected at Docker build time via build args, mapped to
pip extras, so unselected engines' heavy dependencies are never
installed:

```
docker build --build-arg ENGINES=tesseract,pdfplumber,surya,paddleocr .
# → pip install ocrhub[tesseract,pdfplumber,surya,paddleocr]
```

`tesseract` and `pdfplumber` are lightweight and default-on. `surya`
and `paddleocr` are opt-in because they pull in PyTorch/PaddlePaddle.
The Ollama/DeepSeek adapter has near-zero image footprint (it's just
an HTTP client) and is always compiled in; its *availability* is a
runtime check (`OLLAMA_HOST` reachable), not a build-time toggle.

## Error handling

Per-engine failures (missing dependency, model load error, timeout,
malformed file for that engine) are captured as `OcrResult.error` for
that engine only. Running 3 engines on one document where 1 fails
still returns results for the other 2 — never a hard 500 for a
partial failure.

## Testing

- Unit tests per adapter against a small fixture set: a clean scan,
  a skewed/noisy scan, a born-digital PDF, a multi-page PDF.
- Integration test hitting the REST API end-to-end for at least one
  CPU-only engine (Tesseract) in CI.
- GPU-dependent engines (Surya, PaddleOCR, Ollama) are skipped in CI
  and tested locally/manually before release.

## Risks

- **PaddleOCR install fragility** (known from prior experience): pin
  exact versions once a working combination is found; document the
  working install path in the README rather than debugging it live
  during initial build-out.
- **Ollama dependency is external**: if `OLLAMA_HOST` isn't set or
  isn't reachable, the DeepSeek adapter must degrade to "unavailable"
  in `GET /engines`, never a startup crash.

## Repo & publishing

- Public GitHub repo, MIT license.
- README: why it exists (born from two prior OCR pipeline projects),
  quickstart (`docker build` / `docker run` with engine selection),
  an engine comparison table, and a brief, non-pushy author/business
  attribution footer.
- Reddit post once `docker run` → working UI is verified end to end
  locally.

## Explicitly out of scope for v1

- EasyOCR, docTR, datalab.io API, LandingAI API adapters.
- Bundling Ollama itself or pulling model weights automatically.
- Multi-container/microservice split per engine.
- Runtime engine install (all engine selection is build-time).
